# apps/www — Deployment Plan (self-hosted Dokploy)

Status: **files written, awaiting local verify → Dokploy** Target: a self-hosted
Dokploy VPS; Traefik routes via the **Domains** tab. Reference implementation:
`~/work/next101/next101` (`Dockerfile`, `compose.yml`, `docs/deploy-plan.md`).

## 1. Decisions

| Decision        | Choice                                                                              | Rationale                                                                                           |
| --------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Topology        | One Dokploy **Docker Compose** service: `app`                                       | The site has no database and no persistent state — a single service is the whole deployment         |
| Base image      | `node:24-bookworm-slim`                                                             | Current LTS, Debian slim; same base as next101                                                      |
| Package manager | `npm install -g pnpm@11.13.0` (no Corepack)                                         | Must match the pin in `.github/workflows/*.yml` and the generator of `pnpm-lock.yaml` (lockfile v9) |
| Build context   | **Repository root**                                                                 | `apps/www` consumes the workspace package `packages/fumandocs-ui`, which is built inside the image  |
| Image strategy  | Full production `node_modules` + `next start` (**no** `output: 'standalone'` in v1) | Simplest reliable path on a pnpm workspace; standalone is the documented upgrade (§10)              |
| State           | None — no volumes, no migrations                                                    | Content is MDX compiled at build; the only server route is `/api/search`                            |
| CI/CD           | Dokploy builds from git on deploy                                                   | Same as next101; move to prebuilt images only if server builds hurt (§10)                           |

## 2. Findings that shaped this plan

- **It is a pnpm workspace, not a single package.** `pnpm-workspace.yaml` covers
  `packages/*` and `apps/*`; the lockfile has importers for `.`, `apps/www`,
  `packages/fumandocs-ui`, `packages/create-fumandocs`. The `deps` stage
  therefore copies _every_ workspace manifest — with one missing,
  `--frozen-lockfile` cannot reconcile the importers.
- **`fumandocs-ui` must be built before `next build`.** `apps/www`'s own build
  script already does this (`pnpm --filter fumandocs-ui build && next build`),
  so one `pnpm --filter fumandocs-www build` is enough.
- **`.source/` is generated, not committed** (`apps/www/.gitignore` ignores it).
  It is regenerated by the `fumadocs-mdx` Next plugin during `next build` —
  proven by `test.yml`, which builds the site on a clean checkout. No extra
  codegen step is needed.
- **The root `prepare` script breaks a git-less install.** `lefthook install`
  exits 1 outside a git repository (verified locally), and `node:bookworm-slim`
  has no `git` binary at all. `.git` is excluded from the build context, so
  `prepare` now runs `scripts/setup-git-hooks.mjs`, which skips lefthook unless
  git reports a work tree, and the `deps` stage still installs with
  `--ignore-scripts`. No dependency needs a build script: esbuild's only
  validates the prebuilt platform binary that ships as an optional dependency.
- **pnpm ≥11 will install behind your back when it judges the tree stale.**
  Every `run`/`exec` is preceded by a dependency-status check
  (`verify-deps-before-run`, default `install`); the install it then spawns does
  **not** inherit `--ignore-scripts`. The first Dokploy build died exactly
  there: an install nobody wrote, then `prepare` → `lefthook install` →
  `exec: "git": executable file not found in $PATH`. The trigger was the install
  tree — `deps` gives every workspace project its own `node_modules`, but the
  runner stage copied only the root one, so `apps/www` was "a package with
  dependencies but no modules directory". Fix, both halves: the runner now
  copies the whole installed tree, and the build step sets
  `pnpm_config_verify_deps_before_run=false`.
- **`SITE_URL` is a build-time value.** `lib/site.ts` reads it and it feeds
  `metadataBase`, OpenGraph URLs, `sitemap.xml` and `robots.txt`, all of which
  are prerendered. It must be a build arg, not only a runtime env var.
- **`next` is not on the root `.bin`** under pnpm — the binary lives at
  `apps/www/node_modules/.bin/next`, which is why the CMD sets that working
  directory.
- **The slim image has no `curl`/`wget`**, so the healthcheck uses
  `node -e "fetch(...)"`.

## 3. Architecture

```
                    ┌──────────── Dokploy server ────────────┐
 Internet ── traefik ──► app (built from repo Dockerfile)    │
             TLS        │   next start :3000                 │
                        │   ├─ prerendered docs + landing    │
                        │   └─ /api/search (on demand)       │
                        └────────────────────────────────────┘
```

No external services are contacted at runtime. No host `ports:` mapping —
Dokploy proxies to container port 3000.

## 4. Repo files

| File            | Purpose                                                                                          |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `Dockerfile`    | 3 stages on `node:24-bookworm-slim`: `base` (pnpm) → `deps` (install) → `runner` (build + start) |
| `.dockerignore` | Shrinks the build context; keeps `.git` out (hence `--ignore-scripts`)                           |
| `compose.yml`   | Single `app` service, build args, healthcheck                                                    |
| `.env.example`  | Template for the Dokploy Environment tab and local compose                                       |

## 5. Image build

1. `base` — Node 24 + `pnpm@11.13.0` installed with `npm install -g` (no
   Corepack).
2. `deps` — copies the root manifests plus each workspace `package.json`;
   `pnpm install --frozen-lockfile --ignore-scripts`. Cached until a manifest or
   the lockfile changes.
3. `runner` — copies the whole installed workspace tree from `deps` (root
   `node_modules` **and** the per-project ones), copies the source,
   `ARG SITE_URL` → `ENV`,
   `pnpm_config_verify_deps_before_run=false pnpm --filter fumandocs-www build`,
   then a non-root user (uid/gid 1001) owns `/app`.

**Why not `output: 'standalone'` in v1.** Standalone emits a traced
`.next/standalone` bundle that shrinks the runtime image a lot, but with a pnpm
workspace the trace has to cover `packages/fumandocs-ui/dist` and the hoisted
store, which means setting `outputFileTracingRoot` and re-verifying that CSS and
assets survive the trace. Not worth the risk for the first deploy — see §10.

## 6. Environment variables

| Variable                  | Phase                   | Value                                                                             |
| ------------------------- | ----------------------- | --------------------------------------------------------------------------------- |
| `SITE_URL`                | **build arg** + runtime | Public origin, e.g. `https://docs.example.com`. Rebuild the image when it changes |
| `NODE_ENV`                | runtime                 | `production` (set in the image and compose)                                       |
| `HOSTNAME` / `PORT`       | runtime                 | `0.0.0.0` / `3000` (set in the image and compose)                                 |
| `NEXT_TELEMETRY_DISABLED` | runtime                 | `1`                                                                               |

That is the complete list — there are no secrets, no database URLs and no
third-party keys.

## 7. Local verification

```sh
cp .env.example .env          # set SITE_URL (http://localhost:3000 is fine)
docker compose -f compose.yml build
docker compose -f compose.yml up
# uncomment `ports:` in compose.yml to reach http://localhost:3000
```

Check the landing page, `/docs`, `/docs/getting-started`, `/sitemap.xml`,
`/robots.txt`, and the search dialog (`/api/search`).

## 8. Dokploy setup (one-time)

1. **Prereqs**: Dokploy on the VPS; DNS A record for the domain pointing at the
   server.
2. **New Project → Docker Compose** → this repo + branch, compose path
   `compose.yml`.
3. **Environment**: set `SITE_URL` to the public HTTPS origin (it is also the
   build arg).
4. **Domains**: service `app`, port `3000`, HTTPS on.
5. **Deploy** → the build log should show `pnpm --filter fumandocs-www build`
   completing, and the container log `▲ Next.js ... Ready`.
6. Smoke test the domain: landing page, `/docs`, `/docs/getting-started`,
   `/sitemap.xml`.
7. Enable the auto-deploy webhook if you want pushes to redeploy.

**Rollback:** Dokploy keeps previous deployments — redeploy an older record to
rebuild from that commit. There is no schema or state to roll back.

## 9. Ops

- Logs: Dokploy's build log (per deploy) and container log (`next start`).
- If a build fails before `next build` prints anything, suspect pnpm's pre-run
  dependency check — it runs an install from inside whatever layer it is in.
  `pnpm_config_verify_deps_before_run=error` makes it name the problem instead
  of acting on it
  (`pnpm_config_verify_deps_before_run=error pnpm --filter fumandocs-www build`
  prints e.g. _"Workspace package fumandocs-www has dependencies but does not
  have a modules directory"_).
- No volumes or backups — nothing is persisted.
- The healthcheck hits `/` every 30s; `restart: unless-stopped` covers crashes.

## 10. Out of scope (upgrade paths)

- `output: 'standalone'` +
  `outputFileTracingRoot: path.join(__dirname, '../..')` to shrink the image
  (then `node apps/www/.next/standalone/.../server.js`), and drop the full
  `node_modules` copy.
- Prebuilt images in a registry (GHCR) pushed from CI, so the VPS only pulls.
- Prune dev dependencies after the build
  (`pnpm --filter fumandocs-www... --prod deploy` style) to cut image size while
  keeping `next start`.
- A dedicated `/api/health` route and a container-level healthcheck on `app`.
- A staging Dokploy environment (e.g. `staging.docs.example.com`) from the same
  compose file.
